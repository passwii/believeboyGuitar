# 电吉他学习资料库 — 设计文档

日期：2026-10-15
状态：已确认，待进入实现计划

## 1. 项目目标

构建一个**纯前端的个人电吉他学习资料库**。

要解决的核心问题不是"展示资料"，而是把收集到的原始资料**改写成结构清晰、直接可读的 HTML 内容**，形成可长期积累的知识资产。原始资料是输入，改写后的页面才是日常查看和复习的对象。

第一版的成功标准：

> 能快速把一份新资料归档，并且之后能按主题、类型或难度把它找回来。

## 2. 范围

### 第一版做什么

- 把原始资料（PDF、图片、文本、曲谱）整理改写成独立 HTML 内容文件
- 用一份清单维护所有资料的元数据，驱动目录、分类与筛选
- 三个页面：学习主页、资料库列表、内容阅读页
- 内容与样式分离：内容页统一套用网站导航与排版样式
- 一致性检查：清单与内容文件不出现脱节

### 第一版明确不做

以下功能在第一版中**全部排除**，等实际使用一段时间、确认真实需要后再评估：

- 练习打卡、进度条、统计图表、复习提醒
- 账号、登录、云同步、任何后端接口或数据库
- PDF 在线阅读器、曲谱播放、自动翻页
- 自动扫描 HTML 生成目录（第一版用人工清单）
- 主题切换、暗色模式、装饰性动效

设计取舍的理由：个人资料库真正的失败模式不是功能少，而是整理了几篇之后就不再更新。第一版的所有取舍都服务于"容易持续补充"。

## 3. 技术形态

- Next.js（App Router）+ TypeScript + Tailwind CSS
- 纯前端，可静态导出
- 无后端、无数据库、无账号体系
- 数据来源是项目内的文件，构建时读取

## 4. 目录结构

```
content/
  manifest.ts          ← 清单：所有资料的元数据（单一事实来源）
  lessons/
    <slug>.html        ← 每份改写后的资料正文，一个文件一篇
  content.css          ← 内容区排版样式
app/                   ← 页面外壳：导航、列表、内容页渲染
inbox/                 ← 原始资料投放处（不纳入版本库）
archive/               ← 整理完成后的原始资料归档（不纳入版本库）
docs/superpowers/      ← 设计文档与实现计划
```

`inbox/` 与 `archive/` 不纳入版本库：原始资料通常体积大且涉及版权，版本库只保留改写后的成果与来源说明。

## 5. 内容模型

`content/manifest.ts` 中每条记录包含：

| 字段 | 类型 | 作用 |
|---|---|---|
| `slug` | string | 唯一标识，对应 `lessons/<slug>.html` |
| `title` | string | 标题 |
| `summary` | string | 一句话简介 |
| `stage` | string | 学习阶段，如「入门 / 基础 / 进阶」 |
| `topics` | string[] | 主题，如「乐理 / 技巧 / 音阶与指板 / 曲谱 / 设备与音色」 |
| `tags` | string[] | 自由标签 |
| `difficulty` | 1–5 | 难度 |
| `source` | string | 来源出处与版权说明 |
| `updatedAt` | string | 最近整理时间 |

清单是**单一事实来源**：网站的所有目录、分类、筛选都从这里生成。出现问题时容易定位，不会出现"文件在但目录里没有"的情况。

主页的"近期学习目标"同样是清单中的一段简单配置，不做打卡或进度系统。

## 6. 页面

### 主页 `/`

- 近期学习目标（清单中的一段手写配置）
- 最近整理的几份资料
- 资料库入口

刻意保持轻量，不承担管理功能。

### 资料库 `/library`

- 全部资料的卡片列表
- 按主题、学习阶段、难度筛选
- 按标题和标签搜索

### 内容页 `/library/<slug>`

- 统一导航
- 正文区渲染该资料的 HTML 内容
- 附来源信息与最近更新时间

## 7. 样式策略

- 先朴素，可读优先：一个中性色 + 一个强调色，系统字体栈
- 内容区限制在舒适阅读宽度
- 曲谱、指法图等特殊排版，等第一份真实资料到来后针对性添加，不预先设计

### 内容 HTML 的硬约束

内容文件只写**语义标签**（`h2`、`p`、`ul`、`table` 等），不写行内样式、不写自带导航。样式完全由网站控制。这是"统一视觉"能成立的关键前提。

### 独立 HTML 的边界

每份资料独立成一个文件，但它是**内容片段**（一个 `<article>`），不是自带导航的完整网页。直接用浏览器打开可以看到结构完整、样式朴素的内容；完整阅读体验通过网站获得。

## 8. 工作流

日常工作的五个步骤：

1. 把原始资料（PDF、图片、文本、曲谱）放进 `inbox/`
2. 阅读、提炼、改写，产出 `content/lessons/<slug>.html`
3. 更新 `content/manifest.ts` 登记元数据
4. 本地预览，确认内容准确、可读
5. 原始资料移到 `archive/`

## 9. 验证方式

验证分两层，因为项目的核心资产是内容质量而非工程复杂度。

### 内容层

- 每次整理完成后，在浏览器中打开实际页面截图，确认文字、表格、示例排版正常
- 有原始资料可对照时，逐条核对知识点没有走样

### 工程层

- `build` 与类型检查通过
- 一致性检查：清单中每个 `slug` 都能找到对应文件，且不存在游离的孤儿文件

### 人工核对边界

改写是结构重组与语言重写，不是逐字翻译。因此：

- 每份内容都标注来源
- **涉及指法、音阶图、和弦图等"错一个音就练错"的内容，由使用者核对**，不代为拍板

## 10. 落地顺序

1. **先搭项目骨架**：能运行、有导航和页面，但资料库为空
2. **再整理第一份资料**：让内容一进来就能在真实页面中查看效果

先骨架后内容的理由：避免先写完内容才发现外壳不合适。

第一份资料的整理流程：

1. 原始资料放入 `inbox/`
2. 先输出对内容结构的理解——打算怎么分节、哪些地方不确定、哪些够不上事实需要确认
3. 使用者确认或纠正后，产出 HTML 内容与清单条目
4. 浏览器打开实际效果
5. 确认无误后完成
